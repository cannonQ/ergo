## What to look at first

Four problems are HIGH. Each was found by at least two independent reviewers and then checked by a third whose only job was to break it. None of them breaks consensus: legacy and sub-block nodes still agree on which ordering blocks are valid. What they break is liveness and miner income on the sub-block side, and three of the four need no hashrate.

1. **Input-block transactions are checked at the wrong height.** Followers validate an input block's transactions against the parent's context (height h), but the mempool, the miner and the final ordering block all use h+1. One ordinary mempool transaction with an output at creation height h+1 makes every sub-block miner's own input blocks fail, so no first-class transaction is confirmed by sub-block miners while it sits in the pool. One attacker input block holding a transaction valid at h and invalid at h+1 makes every honest sub-block ordering block at h+1 invalid. Storage-rent claims can never land in an input block. (C-1)
2. **The input chain is not bounded by the block limits.** The ordering block carries the whole input chain plus new transactions, but the candidate's cost and size budget covers only the new ones and followers check each input block from cost zero. Once the chain holds just over one block's worth (two transactions of about 4.1M cost each are enough), every ordering block a sub-block miner finds is over the limit and rejected, and the miner regenerates on the same chain. (C-2)
3. **Any peer can replace the body of an already-processed input block.** Transaction ids do not cover spending proofs. One unsolicited code-104 message with the same ids and one altered proof passes the digest check and overwrites the shared transaction cache; nothing re-validates and nothing penalizes. The miner's next ordering candidate commits the tampered transaction and every ordering block it finds in that period is invalid. (C-3)
4. **One 16 MB message can occupy the synchronizer actor for hours.** Weak-id matching is linear per id over the mempool or the block, and code-102 and code-105 messages carry up to 2.7 M ids with no request check and no penalty. A message with duplicate ids costs about K² comparisons with one transaction in the mempool. Header sync, block download and relay wait behind it. (C-4)
